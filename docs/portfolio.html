뮤직매치.
같은 노래에서 시작되는 만남

음악 취향으로 연결되는 대학생 1:1 소개팅 웹앱(PWA). 가입부터 매칭·실시간 채팅·푸시 알림까지 핵심 퍼널 전체가 프로덕션에서 동작합니다.

무엇을 만들었나

사용자가 멜론 차트/검색에서 좋아하는 곡(최대 3개)과 장르를 고르면, 곡·장르가 겹치는 이성과 1:1로 매칭되어 채팅을 시작하는 서비스입니다. 관리자 승인 게이트, 입금 확인, 재매칭 운영 플로우까지 실제 운영을 전제로 한 전체 제품을 혼자 설계·구현·배포했습니다.

음악 기반 매칭

곡·장르 일치 매칭에 교차 학교·연령 확장, 소프트 매칭 폴백까지 단계적 매칭 풀 설계

실시간 채팅

Supabase Realtime 구독, 메시지 수정·삭제(soft delete), 읽으면 사라지는 "펑" 메시지

한 번만 보기 사진

1회 열람 후 스토리지 원본까지 삭제. 워터마크·탭 이탈 가림 등 캡처 억제 장치

둘러보기 모드

비로그인 방문자가 샘플 데이터로 서비스를 미리 체험하고 가입으로 전환되는 퍼널

PWA 푸시 알림

VAPID 기반 Web Push로 매칭·메시지 알림, iOS 홈 화면 설치 유도 배너

운영 도구

승인·재매칭 운영 플로우, Slack 운영 알림, Amplitude/PostHog 행동 분석

기술적 도전과 해결

문제 → 해결 → 검증까지, 대표 사례 네 가지

매칭 동시성 경합

두 탭에서 "매칭 찾기"를 동시에 누르면 같은 유저가 중복 매칭되는 레이스 컨디션

  • find_or_create_match RPC에 Postgres advisory lock + 락 획득 후 상태 재확인 패턴 적용
  • active 매칭 쌍에 부분 유니크 인덱스를 걸어 DB 레벨 이중 안전망 구축
  • k6 부하 테스트로 유저당 VU 3개 동시 난타(더블서밋 재현) 시나리오 작성, 검증 스크립트로 자동 확인
검증 결과 — 5xx 0건 · 중복 매칭 0건

휘발성 콘텐츠 채팅

읽으면 사라지는 메시지와 1회 열람 사진 — 상태가 양쪽 화면에서 동시에, 되돌릴 수 없게 바뀌어야 함

  • 열람 이벤트를 DB에 기록하고 Realtime UPDATE 구독으로 양쪽 화면 동시 소멸 처리
  • "한 번만 보기" 사진은 열람 즉시 스토리지 원본 삭제 — 서버에도 남지 않음
  • 소비(consume) 제약을 SQL 제약조건으로 강제해 클라이언트 우회 차단

보안 — 최소 노출 원칙

소개팅 앱 특성상 프로필·채팅이 민감 데이터 — 클라이언트를 신뢰하지 않는 구조가 필요

  • 전 테이블 RLS 활성 + 정책 본문 감사 스크립트(rls_audit.sql) 운영
  • 매칭 생성·종료 등 쓰기 경로는 SECURITY DEFINER RPC로만 허용
  • 프로필 사진은 비공개 버킷 + 서명 URL, 매칭 상대에게만 노출
  • 공개 가입 액션 rate limit, Realtime 구독 match_id 필터링

외부 API 장애 대응

곡 선택 퍼널이 의존하는 비공식 멜론 API가 간헐적으로 실패

  • 검색 결과 인메모리 캐시(10분)로 반복 호출 절감
  • 장애 시 폴백 곡 목록을 필터링해 반환 — 외부 장애에도 가입 퍼널이 끊기지 않음

데이터 분석과 개선

Supabase + PostHog/Amplitude — 계측을 직접 설계하고, 수치로 이탈 지점을 찾아 제품을 고쳤습니다

계측 설계. PostHog·Amplitude 동시 전송 래퍼를 클라이언트/서버 양쪽에 구축했습니다. 가입·곡 선택처럼 서버 액션에서 리다이렉트되는 "성공" 지점은 브라우저 SDK가 놓치므로 서버에서 ingestion API로 직접 전송하고, distinct_id를 auth user id로 통일해 클라이언트 identify와 병합했습니다. 첫 방문의 UTM·referrer를 first-touch로 저장해 유입 출처별 가입→매칭 퍼널을 볼 수 있게 했고, 이벤트 14개짜리 트래킹 플랜을 문서로 먼저 설계한 뒤 구현했습니다. Supabase DB는 SQL로 직접 분석하고 자체 대시보드로 KPI·퍼널을 시각화했습니다.

데이터가 가리킨 문제 — 실측 지표

가입 → 활성화 퍼널

승인까지는 유지되지만 곡 선택·대화 시작에서 이탈 (명)

공유 장르 수 ↔ 매칭당 평균 메시지

취향이 겹칠수록 대화가 활발 — 음악 매칭 가설 검증

대화 시작률도 62% → 83%로 함께 상승 — 매칭 로직의 취향 가중치를 높이는 근거가 됐습니다.

데이터에서 발견한 문제개선
가입 직후 이탈 심각 — 단일 세션 84%, 승인 대기 페이지가 막다른 길 대기 화면을 "대기 중 할 일" 허브로 전환 — 곡 고르기·둘러보기 CTA로 재방문 동기 부여
가입 퍼널 중도 이탈 — 입력이 많고 결제가 가치 경험보다 먼저 퍼널 단축: 필수 입력을 4개 필드로 축소, 곡 선택을 결제 앞으로 옮겨 가치를 먼저 경험시킴
비로그인 방문자가 내용을 못 보고 이탈 둘러보기 모드 — 샘플 데이터로 미리 체험 후 가입 전환
프로필 사진 필수화가 이탈을 키우는지 불확실 PostHog 피처플래그 기반 useExperiment 훅으로 A/B 실험 설계·검증
계측 장애(Amplitude 미수신)를 배포 후에야 발견 응답 검증 + 부팅 자가진단으로 계측 장애 즉시 감지

아키텍처

DB 접근은 repos/*.server.ts에만, 서버 전용 코드는 *.server.ts 규약으로 격리

품질을 지키는 자동화

  • 색상 가드 — 폐기된 브랜드색이 커밋되면 husky pre-commit이 차단 (lint:colors)
  • db:apply — 마이그레이션을 CLI 한 줄로 적용하는 자체 스크립트
  • 분석 자가진단 — 배포 시점에 Amplitude 미수신을 감지하는 부팅 진단 장치
  • 타입·빌드 게이트 — 모든 변경은 tsc + remix build 통과 후 배포

배운 점

동시성 버그는 부하 테스트로 잡힌다

advisory lock을 넣는 것보다, k6로 경합을 재현해 "5xx 0건·중복 0건"을 수치로 증명하는 과정이 더 중요했습니다.

보안은 기능이 아니라 기본값

RLS를 켜는 것과, 정책 본문이 실제로 최소 권한인지 감사하는 것은 다른 일이었습니다.

외부 의존성은 반드시 실패한다

비공식 API 위에 기능을 쌓을 때는 캐시와 폴백을 처음부터 설계에 포함해야 퍼널이 살아남습니다.

재발 방지는 사람이 아니라 훅이 한다

반복되는 실수는 pre-commit 가드와 스크립트로 프로세스에 박아 해결했습니다.

개선은 감이 아니라 지표에서 시작한다

"단일 세션 84%" 같은 수치가 있어야 어디를 고칠지 정할 수 있었고, 확신 없는 결정은 A/B 실험으로 데이터가 답하게 했습니다.
