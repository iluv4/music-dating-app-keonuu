01 · 문제의 코드

이 30줄 안에 메모리 토픽이 통째로 있다

const store = new Map();   // ← 힙에 사는 무한 성장 캐시

function getCache(key) {
  const entry = store.get(key);
  if (!entry) return null;
  if (Date.now() > entry.expiresAt) {
    store.delete(key);   // 만료 삭제 = "읽을 때만" 일어남
    return null;
  }
  return entry.data;
}

function setCache(key, data, ttl) {
  store.set(key, { data, expiresAt: Date.now()+ttl });
  // ← 상한도 없고, 청소부도 없다
}

주목 3가지: ① store는 모듈 스코프 = 힙에 영구 거주 · ② 만료 삭제는 그 키를 다시 읽을 때만 실행 · ③ 키 개수 상한이 없음. 이 셋이 합쳐지면 사고가 난다.

02 · 어디에 사나

"프로세스 힙 메모리"라는 말의 뜻

📚 스택 (Stack)

  • 함수 호출 때 생기고 끝나면 자동 소멸
  • 지역 변수, 함수 인자
  • 수명 짧음 · 자동 관리 · 안전

🗄️ 힙 (Heap)

  • "오래 들고 있을게" 하고 잡는 공간
  • new Map(), 객체, 배열
  • 내가 delete 안 하면 영원히 잔류

store는 모듈 최상단 const = 함수가 끝나도 안 사라지는 힙에 산다. 그래서 캐시로 쓸 수 있고, 동시에 그래서 위험하다. 스택이면 알아서 청소되지만 힙은 직접 비워야 한다.

03 · 왜 캐시를 두나

메모리 계층 — 빠른 건 작고, 느린 건 크다

CPU 캐시 나노초(ns)
메모리 캐시 (Map) µs ✅ 우리 코드
DB / 디스크 밀리초(ms)
멜론 API (네트워크) 수백 ms

느린 저장소(멜론 API) 앞에 빠른 저장소(Map)를 작게 둬서 자주 쓰는 것만 올린다.
CPU 캐시가 RAM 앞에 있는 것과 완전히 같은 아이디어의 다른 층이다.

04 · 캐시가 통하는 이유

캐시 = 마법이 아니라 행동 패턴에 대한 베팅

⏱️ 시간 지역성
방금 쓴 걸 곧 또 쓴다.
"인기 차트를 한 명이 보면 5분 안에 다른 사람도 같은 차트를 본다" → CACHE_TTL.chart = 5분의 근거.
📍 공간 지역성
방금 쓴 것 근처를 곧 쓴다.
CPU 캐시가 한 바이트가 아니라 한 블록을 통째로 읽어오는 이유.

베팅이 맞으면(같은 차트 재조회) µs에 끝나고, 틀리면(전부 다른 검색어) 캐시는 메모리만 먹는 짐이 된다. → 바로 다음 슬라이드의 사고로 이어진다.

05 · 사고 시나리오

eviction 없는 캐시가 죽는 과정

검색어 캐시가 쌓인다"BTS 신곡" 검색 → set. 그 유저는 다시 검색 안 함 → 아무도 그 키를 다시 읽지 않음 → 만료돼도 영원히 잔류 (만료 삭제는 "읽을 때만")
힙 사용량이 단조 증가차트는 키가 몇 개뿐이라 OK. 하지만 검색어는 유저 입력만큼 무한히 다양 → Map 키 개수가 줄어들 길 없이 계속 증가 = 메모리 누수
cgroups 한도 도달 → OOM KillerRailway가 건 memory.max(예: 512MB)에 부딪힘 → 커널이 회수 시도 실패 → 가장 메모리 많이 먹는 프로세스(=우리 Node)에 SIGKILL. try/catch로 못 잡음, 로그도 안 남고 즉사
Railway 재시작 → 캐시 증발컨테이너의 힙은 컨테이너와 함께 사라짐 → 빈 Map으로 재시작 → 또 차오름 → 또 죽음 (톱니파)
06 · 증상

메모리 그래프가 톱니파(sawtooth)가 된다

올라가다 한도에서 OOM Kill → 재시작으로 뚝 떨어짐 → 다시 상승. 이 톱니 모양 + 주기적 재시작이 메모리 누수의 시그니처. Railway 메트릭에서 이게 보이면 캐시·누수를 의심한다.

oom_score(0~1000)는 대략 "이 프로세스가 메모리를 얼마나 먹나"에 비례. 캐시를 무한히 키운 바로 그 프로세스가 자기 손으로 자길 죽이는 셈. OOM Kill은 JS 예외가 아니라 커널의 SIGKILL이라 try/catch로 못 잡고 유언도 못 남긴다.

08 · 왜 공유가 안 되나

각 프로세스는 자기만의 가상 주소 공간을 가진다

인스턴스 A의 Node

힙 안의 store Map
"BTS 신곡", "차트" …

인스턴스 B의 Node

힙 안의 store Map
(완전히 별개, 텅 빔)

Railway에서 인스턴스를 2개로 늘리면? 두 프로세스의 힙은 커널이 격리한 별개 주소 공간이라 캐시가 공유되지 않는다. A에 캐시된 검색어를 B는 모름 → 히트율 반토막. 진짜 공유하려면 프로세스 밖의 Redis 같은 외부 저장소가 필요하다. "프로세스 간 메모리는 왜 안 나눠지나"가 가상 메모리의 출발점.

09 · 해법

상한 + LRU = OS 페이지 교체와 같은 문제

FIFO

먼저 들어온 것부터 버림. 단순하지만 "오래됐어도 자주 쓰는 것"을 버리는 실수.

LRU ★ 기본값

가장 오래 안 쓰인 것을 버림. "최근에 안 썼으면 앞으로도 안 쓴다" = 시간 지역성 베팅.

LFU

가장 적게 쓰인 것을 버림. 빈도 기반. 구현 복잡.

핵심: RAM이 꽉 차면 OS도 "어느 페이지를 디스크로 내쫓을까?"라는 똑같은 질문을 한다 = 페이지 교체 알고리즘. "캐시 eviction 정책 아세요?"와 "페이지 교체 알고리즘 아세요?"는 사실상 같은 질문이고, 규모와 층만 다르다.

10 · 어떻게 고치나

Map의 "삽입 순서 기억" 성질로 LRU 구현

A (가장 오래됨)
B
C
→ D 삽입

상한 초과 → 맨 앞(가장 오래된 A) 제거 · get 할 때마다 그 키를 지웠다 다시 넣어 맨 뒤로 보냄

// 라이브러리 한 줄이면 끝
import { LRUCache } from "lru-cache";
const store = new LRUCache({
  max: 1000,        // 키 개수 상한 → OOM 원천 차단
  ttl: 5 * 60 * 1000 // 만료도 자동 관리
});

max: 1000 한 줄이 무한 성장을 막는다. 1001번째가 들어오면 가장 오래 안 쓰인 1개가 자동 퇴출 → 메모리가 상한 안에서 평형을 이룬다.

11 · 마무리

🎤 면접 한 줄 정리

  • 스택 vs 힙? "스택은 함수와 함께 자동 소멸하는 단기 메모리, 힙은 직접 해제해야 하는 장기 메모리입니다. 제 캐시 Map은 힙에 있어 비우지 않으면 누수가 납니다."
  • 캐시가 통하는 원리? "시간 지역성 — 방금 쓴 걸 곧 또 쓴다는 베팅입니다. 느린 멜론 API 앞에 빠른 메모리 캐시를 두는 건 CPU 캐시가 RAM 앞에 있는 것과 같은 계층 구조입니다."
  • OOM Killer란? "메모리 한도 초과 시 커널이 oom_score 기준으로 프로세스를 SIGKILL 하는 것입니다. 제 캐시에 상한이 없으면 누수 → OOM → 재시작 톱니파가 됩니다."
  • 해결책? "키 개수 상한 + LRU 퇴출입니다. 이건 OS의 페이지 교체 알고리즘과 같은 문제이고, lru-cache의 max 옵션 한 줄로 원천 차단됩니다."
  • 스케일아웃 시 캐시? "프로세스 힙은 격리돼 인스턴스 간 공유가 안 됩니다. 공유하려면 Redis 같은 외부 저장소가 필요합니다."
