매칭 엔진 — 앱의 심장 💓

"매칭 시작"을 누르면 무슨 일이? 그리고 두 사람이 동시에 누르면 왜 위험한가?

매칭은 두 계층의 합작.
레포 matches.server.ts 는 데이터를 안전하게 조립하고,
DB 함수 find_or_create_match 는 경합을 막는다.

왜 DB 함수(RPC)? "후보 SELECT → matches INSERT → 알림 INSERT"가 하나의 트랜잭션으로 묶여야 안전. 매칭 정책 자체를 DB에 두면 어느 클라이언트에서 불러도 규칙이 일관된다.
후보 선정 규칙

누구를 매칭하나 — 6가지 조건

① 승인 회원
is_approved = true · 본인 제외
② 다른 성별
둘 중 하나라도 null이면 통과(소프트)
③ 다른 전공
major 같으면 제외 (소문자·trim 비교)
④ 다른 동아리
club 같으면 제외 — 지인 거르기
⑤ 곡 겹침 必
user_songs 같은 song_no 1곡↑ EXISTS
⑥ 기존 매칭 X
이미 맺은 쌍은 NOT EXISTS로 제외
조건 통과자 중 order by random() limit 1 — 무작위 1명 선정. 핵심은 ⑤ 음악 취향이 겹쳐야만 매칭된다는 점(이 앱의 정체성).
위험

잠금이 없으면? 경합(race) 발생 ⚠️

함수가 "후보 SELECT → matches INSERT"를 잠금 없이 하면, 두 흐름이 같은 순간 끼어들 수 있다.

(a) 한 사람이 두 번

빠른 더블클릭 / 두 탭 동시 호출
탭1: 내 매칭 없음 확인
탭2: 내 매칭 없음 확인
탭1: INSERT ✗
탭2: INSERT ✗ → 내가 매칭 2개에

(b) A·B가 서로를

동시에 상대로 선택
A: 후보=B 확인
B: 후보=A 확인
A: INSERT(A,B)
B: INSERT(A,B) → 같은 쌍 active 2행
증상: 한 사람이 동시에 여러 매칭, 또는 한 쌍에 채팅방 2개. 데이터 정합성이 깨진다.
해결

3중 방어 🛡️

1
Advisory Lock — pg_advisory_xact_lock(hashtext('match_creation'))
매칭 생성 구간을 트랜잭션 단위로 직렬화. 한 번에 한 명만 통과.
2
락 후 재확인 — 잠금 기다리는 동안 다른 호출이 나를 이미 매칭시켰을 수 있음 → 다시 SELECT.
대기 중 생긴 매칭을 발견하면 그걸 반환(멱등).
3
부분 유니크 인덱스 (DB 백스톱)
unique (least(a,b), greatest(a,b)) where status='active'
방어가 겹겹인 게 핵심. 락(1)이 앱 로직을 직렬화하고, 인덱스(3)는 그래도 뚫리면 DB가 최후에 거부. 한 겹이 실패해도 다음 겹이 잡는다.
find_or_create_match · 코드

빠른 경로 + 락 + 재확인

-- 빠른 경로: 이미 매칭 있으면 잠금 없이 즉시 반환 (멱등)
select id into v_match_id from matches
where status='active' and (user_a=p_user_id or user_b=p_user_id);
if v_match_id is not null then return v_match_id; end if;

perform pg_advisory_xact_lock(hashtext('match_creation'));  -- ① 직렬화

-- ② 락 후 재확인: 기다리는 동안 매칭됐을 수 있다
select id into v_match_id from matches where ...;
if v_match_id is not null then return v_match_id; end if;

-- 후보 탐색 → 정규화(least/greatest) → INSERT → 알림 2건
멱등성(idempotent): 같은 사람이 여러 번 불러도 항상 "내 현재 매칭"을 돌려준다. 빠른 경로 + 재확인이 이를 보장.
SECURITY DEFINER

함수 안의 보안 — 신원 검사

create function find_or_create_match(p_user_id uuid)
security definer set search_path to 'public'
...
if auth.uid() is null or auth.uid() <> p_user_id
   then raise exception 'unauthorized'; end if;
if not coalesce(v_me.is_approved, false)
   then raise exception 'not approved'; end if;
  • SECURITY DEFINER: 함수가 소유자 권한으로 실행 → RLS를 넘어 여러 테이블에 INSERT 가능.
  • 그래서 함수 첫 줄에서 auth.uid()로 "정말 너 자신이냐"를 직접 검사. 권한 상승을 함수가 스스로 막는다.
  • set search_path 고정 = search_path 하이재킹 방어 (migration_harden_functions.sql 참고).
matches.server.ts · 레포

읽기 쪽 — 왜 쿼리를 2번 날리나

matches ↔ profiles 사이에 직접 FK가 없다 → PostgREST nested select 불가. 그래서:

① matches 조회or(user_a.eq, user_b.eq)
→
상대 id 모으기
→
② profiles .in(ids)한 번에 일괄
N+1 회피: 매칭마다 프로필을 따로 부르지 않고, 상대 id를 모아 .in() 한 번 + 마지막 메시지 .in() 한 번. Promise.all로 병렬. Map으로 합쳐 조립.
정렬은 카톡처럼 — 마지막 메시지 시각(없으면 매칭 시각) 내림차순.

실전 운영 노트

마이그레이션 적용 시 함정 ⚠️

  • 인덱스 생성 실패: 이미 중복 active 쌍이 있으면 matches_active_pair_uniq 생성이 막힘 → 먼저 중복 정리 후 생성.
  • find_additional_match(재매칭/다중 매칭) 함수는 레포에 본문이 없고 SQL Editor에서만 관리 → 같은 락 + on conflict do nothing을 수동으로 반영해야 함.
  • 같은 락 키('match_creation')를 공유 → 두 함수가 서로에 대해서도 직렬화됨.
  • 적용 경로: SQL Editor 또는 npm run db:apply -- supabase/migration_match_concurrency.sql.
부하 검증: loadtest/match-concurrency.js (k6)로 동시 매칭을 찔러 중복이 안 생기는지 확인할 수 있다.
