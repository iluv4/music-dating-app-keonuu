supabase.server.ts

① 진입점 — 요청마다 새 클라이언트

// 매 요청마다 새로 만들어 쿠키로 세션을 복원한다
export function createSupabaseServerClient(request) {
  const headers = new Headers();
  const supabase = createServerClient(URL, ANON_KEY, {
    cookies: {
      getAll()  { /* 들어온 쿠키 → 세션 복원 */ },
      setAll() { /* 갱신 토큰 → headers에 쌓기 */ },
    },
  });
  return { supabase, headers };
}
왜 매 요청?
서버는 요청을 독립 처리 → 전역 싱글톤 X. 쿠키로 그때그때 세션 복원.
⚠️ 1번 함정
headers를 응답에 안 실으면 세션 갱신이 유실된다. 그래서 모든 json(..., {headers}).
ANON_KEY 사용 → RLS가 적용되는 사용자 권한 클라이언트. 관리자 우회용은 별도 supabase-admin.server.ts.

② 인증 게이트 — 라우트의 문지기

모든 화면이 진입하자마자 게이트 함수 하나를 호출. 권한이 사다리처럼 쌓여 있다.

getUser 세션만 확인 · 없으면 null 반환(리다이렉트 X)
requireUser 없으면 → /login
requireApprovedUser 프로필 없음 → /profile/basic · 미승인 → /waiting
requireMatchAccess + "이 채팅방이 내 것인가" → /chat
throw redirect(...): loader 안에서 redirect를 던지면 즉시 흐름 중단. return이 아니라 throw라 깊은 중첩에서도 탈출 가능.
이 한 함수가 곧 비즈니스 규칙. requireApprovedUser를 읽으면 가입 퍼널의 상태 전이도가 그대로 보인다.
상태 머신

가입 퍼널 = 코드에 박힌 상태 전이도

방문 (비로그인)
↓ 로그인
프로필 없음 → /profile/basic

approvedUserOrGuest는 다르다 — 비로그인을 막지 않고 { guest: true }를 반환. "둘러보기"의 핵심: 막는 대신 게스트 신분증을 발급해 화면이 알아서 분기.

여기서 배우는 설계 의사결정 3

  • DB 로직은 SQL 함수(RPC)로. 복잡한 매칭 조건을 JS가 아닌 Postgres 함수에 → 그래서 supabase/*.sql 읽기가 중요.
  • PII 방어가 코드에 명시. 승인회원도 maskName()으로 실명 마스킹, 게스트엔 이름·학교 없는 preview만.
  • 하나의 화면, 세 신분. loader가 넘긴 guest/loggedIn 플래그로 분기.
