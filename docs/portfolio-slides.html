기술적 도전 1 / 4

매칭 동시성 경합

Problem두 탭에서 "매칭 찾기"를 동시에 누르면 같은 유저가 중복 매칭되는 레이스 컨디션
  • find_or_create_match RPC에 Postgres advisory lock + 락 획득 후 상태 재확인
  • active 매칭 쌍 부분 유니크 인덱스 — DB 레벨 이중 안전망
  • k6 부하 테스트로 유저당 VU 3개 동시 난타(더블서밋 재현) + 자동 검증 스크립트
검증 결과 — 5xx 0건 · 중복 매칭 0건
기술적 도전 2 / 4

휘발성 콘텐츠 채팅

Problem읽으면 사라지는 메시지·1회 열람 사진 — 상태가 양쪽 화면에서 동시에, 되돌릴 수 없게 바뀌어야 함
  • 열람 이벤트를 DB에 기록, Realtime UPDATE 구독으로 양쪽 화면 동시 소멸
  • "한 번만 보기" 사진은 열람 즉시 스토리지 원본 삭제 — 서버에도 남지 않음
  • 소비(consume) 제약을 SQL 제약조건으로 강제 — 클라이언트 우회 차단
  • 워터마크 · 우클릭/드래그 차단 · 탭 이탈 가림으로 캡처 억제
기술적 도전 3 / 4

보안 — 최소 노출 원칙

Problem프로필·채팅이 민감 데이터인 소개팅 앱 — 클라이언트를 신뢰하지 않는 구조가 필요
  • 전 테이블 RLS 활성 + 정책 본문 감사 스크립트(rls_audit.sql)
  • 매칭 생성·종료 등 쓰기 경로는 SECURITY DEFINER RPC로만 허용
  • 프로필 사진은 비공개 버킷 + 서명 URL — 매칭 상대에게만 노출
  • 공개 가입 액션 rate limit · Realtime 구독 match_id 필터
기술적 도전 4 / 4

외부 API 장애 대응

Problem곡 선택 퍼널이 의존하는 비공식 멜론 API가 간헐적으로 실패
  • 검색 결과 인메모리 캐시(10분)로 반복 호출 절감
  • 장애 시 폴백 곡 목록 필터링 반환 — 외부 장애에도 가입 퍼널이 끊기지 않음
데이터 분석 1 / 3

계측을 직접 설계했다

  • PostHog + Amplitude 동시 전송 래퍼 — 클라이언트/서버 양쪽, 키 없으면 no-op
  • 서버 리다이렉트 "성공" 지점은 서버에서 ingestion API 직접 전송, distinct_id 통일로 identify 병합
  • 첫 방문 UTM·referrer first-touch 저장 → 유입 출처별 가입→매칭 퍼널

배운 점

동시성 버그는 부하 테스트로 잡힌다

k6로 경합을 재현해 "5xx 0건·중복 0건"을 수치로 증명하는 과정이 락 자체보다 중요했다

개선은 감이 아니라 지표에서 시작한다

"단일 세션 84%"라는 수치가 고칠 곳을 정했고, 확신 없는 결정은 A/B 실험이 답했다

외부 의존성은 반드시 실패한다

비공식 API 위에는 캐시와 폴백을 처음부터 설계에 포함해야 퍼널이 살아남는다

재발 방지는 사람이 아니라 훅이 한다

반복되는 실수는 pre-commit 가드와 스크립트로 프로세스에 박았다
