커널이 뭐임? 🧠

한 문장 정의 → 부팅 → 중재자 구조 → 시스템 콜 → 유저/커널 모드 → 4대 역할 → 그래서 컨테이너란 — 전부 그림으로

0한 문장 정의

커널은 컴퓨터를 켜면 가장 먼저 메모리에 올라가서, 꺼질 때까지 상주하는 프로그램 하나다.
하는 일은 단 하나 — 하드웨어(CPU·메모리·디스크·네트워크)를 독점 관리하면서, 모든 앱의 "부탁"을 받아 대신 처리해 주는 것.

"운영체제(OS)"라고 부르는 것의 본체가 커널이에요. 바탕화면, 터미널, 설정 앱 같은 건 커널 위에 얹힌 부가 프로그램이고, 리눅스·윈도우·macOS의 진짜 차이는 커널의 차이입니다. Railway 서버라면 = 리눅스 커널.

왜 직접 못 만지게 하나? 아무 앱이나 메모리·디스크를 직접 건드리면, 버그 하나 = 남의 데이터 파괴 = 시스템 전체 다운. 그래서 하드웨어 접근 권한을 커널이 독점하고, 앱은 창구에 줄 서서 부탁만 합니다. 은행 금고(하드웨어)를 손님(앱)이 직접 못 열고 창구 직원(커널)만 여는 것과 같아요.

4유저 모드 vs 커널 모드 — 권한의 벽

🙋 유저 모드 — 앱이 도는 곳

  • 자기 메모리 안에서 계산만 가능
  • 하드웨어 접근 ❌, 남의 메모리 접근 ❌
  • 금지된 짓 시도 → CPU가 막고 커널이 그 앱만 종료
    ("앱 하나 죽어도 시스템은 산다"의 비밀)

👑 커널 모드 — 커널이 도는 곳

  • 모든 메모리·모든 하드웨어에 접근 가능
  • CPU의 특권 명령 사용 가능
  • 여기서의 버그 = 시스템 전체 다운 (블루스크린/커널 패닉)
두 모드 사이의 유일한 합법적 문 = 시스템 콜 · CPU가 하드웨어 수준에서 이 벽을 강제합니다

이 벽이 있어서 모드 전환(유저↔커널)에는 비용이 듭니다. "시스템 콜은 함수 호출보다 비싸다", "컨텍스트 스위칭이 비싸다"는 면접 단골 멘트의 뿌리가 여기예요.

5커널이 하는 일 4가지 — 전부 내 앱과 연결됨

⏱️프로세스 관리 (스케줄링)

CPU 코어는 몇 개 없는데 프로세스는 수백 개 → 커널이 수 ms씩 번갈아 태움(컨텍스트 스위칭). 동시에 도는 것처럼 보이는 착시의 정체.
내 앱: Railway 서버에서 내 node 프로세스가 CPU를 받는 시간을 커널이 배분한다.

🧠메모리 관리 (가상 메모리)

프로세스마다 "메모리 전체가 네 것"인 가상 주소 공간을 주고, 실제 RAM 매핑은 커널이 몰래 관리. 그래서 프로세스끼리 메모리가 격리됨.
내 앱: 멜론 캐시 Map이 인스턴스 간 공유 안 되는 이유. 한도 초과 시 OOM Killer도 커널의 일.

📁파일시스템

디스크는 사실 거대한 바이트 덩어리. "폴더·파일·권한"이라는 개념을 만들어 주는 게 커널.
내 앱: 빌드 결과물 읽기, song-fallback.json 로드가 전부 커널의 read 시스템 콜.

🌐네트워크 / 드라이버

TCP/IP 처리, 패킷 송수신, 각종 장치 제어. 앱은 "소켓"이라는 추상화만 보면 됨.
내 앱: Supabase 쿼리·멜론 API·푸시 발송 — 모든 통신이 커널의 네트워크 스택을 지나간다.

7속이기(namespace) · 제한하기(cgroups) — 커널의 두 가지 기술

🕶️ namespace — 커널이 좁은 세상을 보여줌

내 Node 앱: "프로세스 목록 줘 (ps)"
커널: "다른 손님 앱 200개… 네 프로세스뿐이야 😇"
내 Node 앱: "루트 디렉터리(/) 보여줘"
커널: "여기가 / 야" (실제론 호스트의 한 폴더)
내 Node 앱: "옆에 누구 있어?"
커널: "아무도 없어. 너 혼자야 😇"

벽을 세우는 게 아니라 눈을 가리는 격리. 앱은 옆집의 존재를 알 방법 자체가 없다.

원리: 커널은 모든 프로세스에 "소속 namespace 꼬리표"를 붙여두고, 그 프로세스의 모든 시스템 콜에 꼬리표 기준으로 대답한다. 종류별로 따로 있음 — PID(프로세스 목록: 내 앱은 안에서 PID 1, 호스트에선 PID 48213), mount(파일시스템: 내 빌드 폴더가 / 로 보임), network(내 컨테이너만의 가상 랜카드·IP·자기만의 localhost), user/UTS/IPC 등. Docker도 Railway도 결국 커널의 clone()/unshare() 시스템 콜에 "새 namespace 만들어줘" 플래그를 넣어 호출할 뿐이다.

🔌 cgroups — 커널이 장부 들고 한도 강제

내 컨테이너 메모리한도 512MB
평소: 280MB — 정상 ✅
멜론 캐시 Map이 무한히 쌓이면…
💀 한도 도달 → 커널의 OOM Killer가 내 프로세스만 종료 → Railway 재시작

옆집(다른 손님)은 멀쩡한 이유: 한도가 컨테이너(프로세스 묶음) 단위로 걸려 있어서.

원리: cgroup은 /sys/fs/cgroup/… 아래 폴더로 존재하고, memory.max 같은 파일에 숫자를 쓰면 한도가 걸린다. 이후 커널은 그 그룹 소속 프로세스가 메모리 1쪽(page)을 받을 때마다 장부에 기록. 자원별로 한도의 결과가 다름 — CPU 초과 = 죽이지 않고 천천히(throttle): 시간은 다음 차례에 또 주면 되니까. 앱은 "느려짐"으로 느낀다. 메모리 초과 = 회수 시도 후 OOM Kill: 이미 점유한 공간은 빌려줄 수 없으니까. 앱은 "갑자기 죽음"으로 느낀다. Railway에서 응답이 전반적으로 느려지면 CPU 스로틀, 갑자기 재시작됐으면 OOM을 의심하는 근거가 이것.

8그럼 Railway랑 Docker는 뭐가 다른데?

비교 대상이 아니라 층이 다른 존재입니다. Docker는 컨테이너를 만들고 돌리는 도구(기술), Railway는 그 컨테이너 기술을 대신 운영해 주는 서비스(PaaS)예요. 음식으로 치면 Docker = 밀키트/조리도구, Railway = 풀서비스 식당.

🐳 Docker — 내가 직접 다루는 도구

내가 하는 일
Dockerfile 작성 → docker build이미지(앱+의존성 스냅샷) 만들기
docker run이미지를 컨테이너(프로세스)로 실행
서버 준비·확장·재시작·로그·도메인·HTTPS전부 내 몫 😅
리눅스 커널 (namespace + cgroups)
컨테이너를 "어디서, 어떻게 돌릴지"까지 내가 책임

🚂 Railway — 그걸 다 해주는 서비스

내가 하는 일: git push origin main 끝
Railway가 코드 보고 이미지 자동 빌드railway.json의 build/start 명령 사용 (Dockerfile 없어도 됨)
자기 서버에서 컨테이너로 실행크래시 시 재시작, 로그, 도메인, HTTPS, env 주입까지
리눅스 커널 (namespace + cgroups) — 똑같음 ★
맨 밑 기술은 동일 — 운영을 누가 하느냐만 다름

이 레포에 Dockerfile이 없는 이유: Railway가 railway.json의 npm run build / npm run start를 보고 이미지를 알아서 만들어 주기 때문(빌더가 Dockerfile 역할을 대신). Dockerfile을 직접 두면 Railway는 그걸 우선 사용합니다. 비슷한 층의 비교는 Docker ↔ Podman(도구끼리), Railway ↔ Heroku·Render·Fly.io(서비스끼리), 그리고 그 중간에 "컨테이너 수백 개를 지휘"하는 Kubernetes가 있어요 — Railway 같은 PaaS는 사실상 쿠버네티스급 운영을 대신 해주고 돈을 받는 비즈니스입니다.

🎤 면접 한 줄 정리

  • 커널이란? "부팅 때 메모리에 상주해 하드웨어를 독점 관리하는 OS의 핵심으로, 앱은 시스템 콜로만 자원에 접근합니다. 프로세스 스케줄링·가상 메모리·파일시스템·네트워크가 핵심 역할입니다."
  • 유저/커널 모드는 왜? "앱의 버그가 시스템 전체를 못 망가뜨리게 CPU 수준에서 권한을 나눈 것이고, 그래서 시스템 콜·컨텍스트 스위칭에 모드 전환 비용이 듭니다."
  • 시스템 콜이란? "유저 모드에서 커널 모드로 들어가는 유일한 합법적 통로입니다. 제 앱의 모든 DB 쿼리·API 호출·로그 출력이 결국 시스템 콜입니다."
  • VM vs 컨테이너? "커널을 손님마다 복제하느냐(VM), 하나를 공유하며 namespace로 시야를·cgroups로 자원을 격리하느냐(컨테이너)의 차이입니다. 제 앱이 도는 Railway 컨테이너가 후자입니다."
