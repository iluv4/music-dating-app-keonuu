커널이 뭐임? 🧠

music-dating-app으로 배우는 운영체제 — 커널 편
→ 키 또는 스와이프로 시작
01 · 한 문장 정의

커널 = 하드웨어를 독점 관리하는 상주 프로그램

커널은 컴퓨터를 켜면 가장 먼저 메모리에 올라가서, 꺼질 때까지 상주하는 프로그램 하나다.

하는 일은 단 하나 — 하드웨어(CPU·메모리·디스크·네트워크)를 독점 관리하면서, 모든 앱의 "부탁"을 받아 대신 처리해 주는 것.

"운영체제(OS)"의 본체가 커널. 바탕화면·터미널은 그 위에 얹힌 부가 프로그램이고, 리눅스·윈도우·macOS의 진짜 차이는 커널의 차이다. Railway 서버 = 리눅스 커널.

02 · 부팅

컴퓨터를 켜면 무슨 일이 생기나

→
펌웨어(BIOS/UEFI)하드웨어 점검
→
부트로더디스크에서 커널을 찾음
→
커널을 메모리에 적재 ★이제부터 모든 것의 관리자
→
첫 프로세스(init)→ 그 위에 모든 앱 (node, …)

커널 이후의 모든 프로그램은 커널이 만들어 주는 "프로세스"라는 그릇 안에서 실행된다. 내 Node 앱은 태어나서 죽을 때까지 커널의 관리 아래 있다.

04 · 시스템 콜

내 앱이 Supabase에 쿼리 한 번 보낼 때

유저 공간 — 내 코드의 세계
내 코드: supabase.from("matches").select()repos/matches.server.ts
라이브러리 → Node: fetch → "이 바이트들을 저 서버로 보내줘"
⚡ 시스템 콜 — 커널 공간 진입 (모드 전환)
커널: 소켓 열고 패킷 만들어 네트워크 카드에 직접 명령앱은 여기 못 들어옴
커널: "응답 오면 알려줄게" → 즉시 리턴 (논블로킹)이벤트 루프는 그동안 다른 유저 요청 처리
응답 도착: 네트워크 카드가 커널을 깨움(인터럽트) → 콜백 실행 🎉

파일 읽기, 메모리 할당, console.log까지 — 앱이 바깥세상과 닿는 모든 순간에 시스템 콜이 있다.

05 · 권한의 벽

유저 모드 vs 커널 모드

🙋 유저 모드 — 앱이 도는 곳

  • 자기 메모리 안에서 계산만 가능
  • 하드웨어 ❌, 남의 메모리 ❌
  • 금지된 짓 → CPU가 막고 그 앱만 종료
    ("앱 하나 죽어도 시스템은 산다")

👑 커널 모드 — 커널이 도는 곳

  • 모든 메모리·하드웨어 접근 가능
  • CPU 특권 명령 사용 가능
  • 여기서의 버그 = 시스템 전체 다운
    (블루스크린 / 커널 패닉)
두 모드 사이 유일한 합법적 문 = 시스템 콜 · CPU가 하드웨어 수준에서 강제

모드 전환에는 비용이 든다 → "시스템 콜은 함수 호출보다 비싸다", "컨텍스트 스위칭이 비싸다"는 면접 멘트의 뿌리.

06 · 4대 역할

커널이 하는 일 — 전부 내 앱과 연결됨

⏱️ 프로세스 관리 (스케줄링)

코어 몇 개에 프로세스 수백 개 → 수 ms씩 번갈아 태움(컨텍스트 스위칭). "동시"는 착시.
내 앱: 내 node 프로세스의 CPU 시간을 커널이 배분.

🧠 메모리 관리 (가상 메모리)

프로세스마다 "전부 네 것"인 가상 주소 공간 → 실제 매핑은 커널이 몰래. 프로세스 간 격리의 근원.
내 앱: 멜론 캐시가 인스턴스 간 공유 안 되는 이유. OOM Killer도 커널의 일.

📁 파일시스템

디스크 = 거대한 바이트 덩어리. "폴더·파일·권한" 개념을 만드는 게 커널.
내 앱: song-fallback.json 로드 = read 시스템 콜.

🌐 네트워크 / 드라이버

TCP/IP·패킷 처리. 앱은 "소켓" 추상화만 보면 됨.
내 앱: Supabase·멜론·푸시 — 모든 통신이 커널 네트워크 스택 경유.

08 · 격리 기술 ①

namespace — 커널이 좁은 세상을 보여줌

내 Node 앱: "프로세스 목록 줘 (ps)"
커널: "다른 손님 앱 200개… 네 프로세스뿐이야 😇"
내 Node 앱: "루트 디렉터리(/) 보여줘"
커널: "여기가 / 야" (실제론 호스트의 한 폴더)
내 Node 앱: "옆에 누구 있어?"
커널: "아무도 없어. 너 혼자야 😇"

원리: 모든 프로세스에 "소속 꼬리표"를 붙이고, 모든 시스템 콜에 꼬리표 기준으로 대답한다. 벽이 아니라 눈가리개.
종류: PID(안에선 PID 1, 호스트에선 48213) · mount(내 빌드 폴더가 / 로 보임) · network(나만의 가상 랜카드·IP — 컨테이너의 localhost ≠ 호스트의 localhost!) 등. Docker도 Railway도 결국 clone()/unshare() 시스템 콜에 플래그를 넣을 뿐.

09 · 격리 기술 ②

cgroups — 커널이 장부 들고 한도 강제

내 컨테이너 메모리한도 512MB
평소: 280MB — 정상 ✅
멜론 캐시 Map이 무한히 쌓이면…
💀 한도 도달 → OOM Killer가 내 프로세스만 종료 → Railway 재시작

원리: /sys/fs/cgroup/…/memory.max 파일에 숫자를 쓰면 한도. 이후 페이지 할당마다 장부에 기록.
자원별로 결과가 다름 — CPU 초과 = throttle(죽이지 않고 느리게: 시간은 다음 차례에 또 주면 되니까) vs 메모리 초과 = OOM Kill(점유한 공간은 빌려줄 수 없으니까).
→ Railway에서 전반적으로 느려지면 CPU 스로틀, 갑자기 재시작이면 OOM 의심.

10 · 자주 헷갈리는 것

Railway vs Docker — 층이 다르다

🐳 Docker = 도구

Dockerfile → docker build이미지(앱+의존성 스냅샷) 만들기
docker run이미지를 컨테이너로 실행
서버·확장·재시작·도메인·HTTPS전부 내 몫 😅
리눅스 커널 (ns + cgroups)
밀키트와 조리도구

🚂 Railway = 서비스 (PaaS)

내가 하는 일: git push 끝
이미지 자동 빌드railway.json의 build/start 사용 — Dockerfile 없어도 됨
컨테이너 실행 + 재시작·로그·도메인·env까지
리눅스 커널 (ns + cgroups) — 똑같음 ★
풀서비스 식당

올바른 비교 짝: Docker ↔ Podman(도구), Railway ↔ Heroku·Render·Fly.io(서비스). 이 레포에 Dockerfile이 없는 이유 = Railway 빌더가 그 역할을 대신하기 때문.

11 · 한 층 더

Docker 이미지/레이어는 정확히 뭔가

📦 이미지 = 읽기 전용 레이어의 겹침

컨테이너의 쓰기 레이어실행 중 변경분만 — 지우면 증발 (copy-on-write)
레이어 4: 내 소스 코드 + 빌드 결과COPY . / npm run build
레이어 3: node_modulesCOPY package.json + npm install
레이어 2: Node 런타임node:20 베이스
레이어 1: 리눅스 기본 파일들debian 등 — 커널은 없음! (호스트 것 사용)
각 레이어 = "이전 층과의 차이(diff)" 스냅샷

왜 굳이 겹겹이?

캐시: 소스만 바꾸면 레이어 4만 다시 빌드package.json을 소스보다 먼저 COPY하는 관례의 이유
공유: 이미지 100개가 같은 node:20 레이어를 디스크에 1번만 저장pull 할 때도 없는 레이어만 받음
불변: 이미지는 읽기 전용 → 어디서 실행해도 동일"제 컴퓨터에선 되는데요" 문제 해결
커널 기술: overlayfs여러 층을 겹쳐 하나의 파일시스템처럼 보여줌 + mount namespace로 그걸 / 라고 속임

이미지 = 붕어빵 틀(파일 스냅샷 + 시작 명령), 컨테이너 = 붕어빵(틀에서 찍어낸 실행 프로세스). 컨테이너의 쓰기 레이어는 컨테이너와 함께 사라진다 → Railway 재배포마다 새 이미지·새 컨테이너 = 멜론 캐시·임시 파일이 증발하는 이유. 영구 보관할 데이터는 그래서 컨테이너 밖(Supabase)에 둔다.

12 · 마무리

🎤 면접 한 줄 정리

  • 커널이란? "부팅 때 메모리에 상주해 하드웨어를 독점 관리하는 OS의 핵심으로, 앱은 시스템 콜로만 자원에 접근합니다. 프로세스 스케줄링·가상 메모리·파일시스템·네트워크가 핵심 역할입니다."
  • 유저/커널 모드는 왜? "앱의 버그가 시스템 전체를 못 망가뜨리게 CPU 수준에서 권한을 나눈 것이고, 그래서 시스템 콜·컨텍스트 스위칭에 모드 전환 비용이 듭니다."
  • 시스템 콜이란? "유저 모드에서 커널 모드로 들어가는 유일한 합법적 통로입니다. 제 앱의 모든 DB 쿼리·API 호출·로그 출력이 결국 시스템 콜입니다."
  • VM vs 컨테이너? "커널을 손님마다 복제하느냐(VM), 하나를 공유하며 namespace로 시야를·cgroups로 자원을 격리하느냐(컨테이너)의 차이입니다. 제 앱이 도는 Railway 컨테이너가 후자입니다."
  • Docker vs Railway? "Docker는 컨테이너를 만들고 돌리는 도구, Railway는 그 빌드·실행·운영을 대신해 주는 PaaS입니다. 밑단 기술(namespace/cgroups)은 동일합니다."
  • 이미지와 레이어? "이미지는 읽기 전용 레이어를 overlayfs로 겹친 파일 스냅샷이고, 컨테이너는 그 위에 쓰기 레이어 하나를 얹은 실행 인스턴스입니다. 레이어 덕분에 빌드 캐시와 저장 공간 공유가 가능합니다."
