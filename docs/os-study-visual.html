check-then-act(확인 후 행동) 사이에 다른 실행 흐름이 끼어드는 것이 경쟁 상태. pg_advisory_xact_lock(hashtext('match_creation'))은 임계 구역에 한 번에 하나만 들어가게 하는 뮤텍스(상호 배제)이고, _xact_(트랜잭션 락)이라 프로세스가 죽어도 락이 고아로 남지 않는다. 전역 락 하나 = 거친 입도(coarse-grained) → 안전하지만 직렬화 병목. 유저별 락으로 쪼개면 빨라지지만, 두 락을 잡는 순서가 엇갈리면 순환 대기 → 데드락. 해법은 락 정렬(작은 id부터 잡기). 유니크 인덱스는 락이 뚫려도 막아주는 최후 방어선, k6 부하 테스트는 타이밍 의존적인 race를 강제로 재현하는 도구.

3메모리 — 멜론 캐시와 OOM Killer

📄 src/lib/melona-cache.server.ts — const store = new Map() (프로세스 힙 메모리)
CPU 캐시 — ns
메모리 캐시 (Map) — µs ✅
DB / 디스크 — ms
멜론 API (네트워크) — 수백 ms
↑ 빠르고 작다 · 아래로 갈수록 느리고 크다
캐시가 통하는 이유 = 시간 지역성(같은 차트를 5분 안에 또 본다)
잠재 시나리오 — eviction 없는 캐시의 최후
검색어 캐시가 Map에 쌓임만료 키는 "읽을 때만" 삭제 → 안 읽히면 영원히 잔류
힙 사용량이 계속 증가각 프로세스는 자기만의 가상 주소 공간을 가짐
cgroups 메모리 한도 도달 → OOM Killer가 Node 프로세스 강제 종료커널이 점수(oom_score) 매겨 희생자 선택
Railway가 컨테이너 재시작 → 캐시 전부 증발해법: 키 개수 상한 + LRU(가장 오래 안 쓴 것 제거) = 페이지 교체 알고리즘과 동일한 아이디어

인스턴스를 2개로 늘리면? 프로세스 메모리는 격리되므로 캐시가 공유되지 않는다 → 공유하려면 IPC 또는 외부 저장소(Redis). "프로세스 간 메모리 공유가 왜 안 되는가"가 가상 메모리의 출발점.

🎤 면접에서 이렇게 말하기

  • 동시성: "매칭 더블서밋으로 중복 매칭이 가능해서, advisory lock으로 임계 구역을 보호하고 유니크 인덱스를 최후 방어선으로 둔 뒤, k6로 경쟁을 재현해 5xx 0건·중복 0건을 검증했습니다."
  • 이벤트 루프: "Node는 싱글 스레드지만 I/O를 OS에 위임하므로 동시 요청을 처리합니다. 그래서 CPU 작업인 이미지 처리는 클라이언트로 보냈습니다."
  • 메모리: "인메모리 캐시는 프로세스 단위라 스케일아웃하면 공유가 안 되고, eviction이 없으면 컨테이너 메모리 한도에서 OOM Kill 됩니다. LRU 상한이 페이지 교체와 같은 아이디어입니다."
  • 컨테이너: "Railway 컨테이너는 VM과 달리 호스트 커널을 공유하고 namespace + cgroups로 격리된 프로세스입니다."
